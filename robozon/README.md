# Робозон, Задача 1 — Имитационная модель сортировочного центра

**Команда: Ящик Шрёдингера** (yashchik_shryodingera_517)

Имитационная модель (цифровая копия процессов, где события разыгрываются
во времени) сортировочного центра Ozon: 100 000 товаров/час, 400 направлений,
полный контур от приёмки палет до ворот отгрузки, с максимальной автоматизацией.

## Быстрый старт

```bash
# 1. Зависимости (Python 3.11+)
pip install -r requirements.txt

# 2. Смоук-тест: 2 часа модельного времени (~10–30 с реального)
make smoke

# 3. Полный суточный прогон (метрики за 1 мин / 1 ч / 12 ч / 24 ч)
make run

# 4. Дашборд с графиками (после прогона)
make dashboard
```

Или в Docker (воспроизводимость для проверки экспертами):

```bash
make docker
```

## Стек и подход к моделированию

| Слой | Инструмент | Почему |
|---|---|---|
| Ядро симуляции | **SimPy** (Python, дискретно-событийное моделирование) | Из перечня рекомендованного open-source ПО организаторов; полный контроль логики; прозрачность кода |
| Расчёты/распределения | **NumPy** | Парето-веса направлений, розыгрыш направлений |
| Метрики | CSV + JSON (стандартная библиотека) | Нейтральные форматы из требований ТЗ |
| Дашборд | **Streamlit + Plotly** | Изменение параметров и графики без пересборки |
| Балансировка направлений | LPT-эвристика → **Google OR-Tools** (v0.2) | Дробление тяжёлых направлений по сортерам |
| Воспроизводимость | **Docker**, Makefile | Один-в-один запуск в среде проверки |

Подход: полноценная имитационная модель (не только аналитика) поверх
обязательной аналитической модели — см. `docs/analytical_model.md`.

## Состав учтённых процессов (полнота — критерий 2.1)

Приёмка палет в буфер (185/ч) → депаллетизация (стрейч, лента) →
транспортировка КТЯ (картонный тарный ящик) → вскрытие КТЯ →
инфид (перекладка товаров в сортировку, авто/ручной режим) →
отщеп nonsort-потока → ручная сортировка nonsort → роллкейджи →
автосортировка по 400 направлениям (N сортеров, дробление тяжёлых
направлений) → скаты: наполнение выходных КТЯ (закрытие по 27 шт
или таймауту) → контур тары (80% реюз / 20% брак / машина новых) →
заклейка → транспортировка → буфер отгрузки → палетизация (20 КТЯ) →
ворота отгрузки (24 шт, машина = 16 палет КТЯ + 16 роллкейджей, 2 ч).

## Ключевые входные параметры (`config.yaml`)

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `flow.items_per_hour` | 100 000 | входящий поток [ТЗ] |
| `flow.p_nonsort` | 0.05 | доля nonsort (в ТЗ не задана — параметр) |
| `sorters.count` | 11 | число сортеров (10 = нулевой резерв) |
| `sorters.assignment_mode` | split | split/strict — дробление направлений |
| `infeed.mode` | auto | auto/manual — главный рычаг автоматизации |
| `chutes.fill_timeout_min` | 45 | таймаут закрытия неполного КТЯ |

Любой параметр меняется из CLI без правки кода:
`python -m src.run --set sorters.count=10 --set flow.p_nonsort=0.08`

## Сценарии (make-цели)

- `make run` — базовый суточный прогон (11 сортеров, авто-инфид)
- `make scenario-tight` — 10 сортеров: демонстрация нулевого резерва
- `make scenario-manual` — ручной инфид: сравнение уровня автоматизации
- `make smoke` — быстрая проверка (2 часа)

## Результаты прогона (`data/out/`)

- `operations_minutely.csv` — счётчики по каждой операции поминутно
- `operations_agg.csv` — агрегаты окнами 1 мин / 1 ч / 12 ч / 24 ч
- `queues.csv` — длины очередей/буферов
- `utilization.csv` — загрузка ресурсов (0–1)
- `summary.json` — сводка: балансы потоков, конфиг, режимы

## Логика модели кратко

Единица потока — КТЯ, товары учитываются счётчиками (см. допущение A-01).
Направление каждого товара разыгрывается по весам Ципфа, подобранным
под правило «20% направлений = 80% объёма» из ТЗ. Тяжёлые направления
автоматически дробятся между сортерами (иначе топ-направление,
~18,6 тыс. тов/ч, перегружает любой одиночный сортер). Все операции
пишут метрики в минутные бакеты; загрузка ресурсов считается по
занятому времени. Балансовая сверка (вход = сортировка + nonsort +
незавершёнка) выполняется в конце каждого прогона.
